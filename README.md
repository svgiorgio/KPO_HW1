# Проект «ВышКат»

Консольное приложение для учёта парка кикшеринга. 
Написано на Python 3.15 с использованием ООП, SOLID, DI-контейнера и юнит-тестов.

## Запуск

```bash
pip install -r requirements.txt
python main.py
```

## Тестирование

```bash
pytest --cov=src
```

### 1. Какой принцип SOLID применён наиболее явно и где?
**Dependency Inversion (D)**. Класс `ServiceCenter` зависит от абстракции `InspectionRule`, а не от конкретной реализации. В `main.py` через DI-контейнер передается конкретное правило `EnergyLimitRule`, но сам сервис об этом не знает.

### 2. Какой принцип SOLID сознательно ограничен / «почти нарушен» и почему это приемлемо?
**Interface Segregation (I)**. Интерфейсы разделены на `Inventorizable` и `EnergyConsumer`. Однако для фильтрации новичков не стал создаваться отдельный интерфейс `NoviceFriendly`, вместо этого используется проверка `hasattr(device, "novice_friendliness")`. Это осознанное упрощение: создавать отдельный интерфейс ради одного метода избыточно. Если в будущем появится больше методов, связанных с новичками, они будут выделены в отдельный протокол.

### 3. Что сломается при добавлении нового вида транспорта, сотрудника или склада запасов?
- **Новый транспорт:** ничего не сломается. Достаточно создать класс-наследник `Transport` (и `EnergyConsumer`, если он потребляет энергию). Ядро (`Fleet`, `ServiceCenter`) не меняется.
- **Сотрудник:** по ТЗ сотрудники не ставятся на баланс. Если их добавить, они не будут наследовать `Inventorizable`, поэтому логика парка их просто не увидит.
- **Склад запасов:** это отдельная сущность. Появится новый сервис (например, `Warehouse`), который не затронет логику `Fleet`.

### 4. Какой тест фиксирует решение техосмотра / правило «для новичков»? Как подменяется зависимость?
Решение техосмотра фиксируют тесты `test_inspection_accepts` и `test_inspection_rejects` в `tests/test_services.py`.
Подмена зависимости проверяется в `tests/test_di.py` в функции `test_di_substitution`. Создается класс `FakeRule`, который всегда отклоняет устройства, и передается в `ServiceCenter` вместо реального правила. Тест доказывает, что благодаря DI можно менять поведение системы в тестах, не трогая основной код.

### 5. Что сделал ИИ, а что изменили вы?
ИИ использовался как вспомогательный инструмент для генерации шаблонов классов и написания первичных тестов. Архитектура, разделение на интерфейсы и логика DI-контейнера спроектированы вручную, настроена работа с техосмотром и переписаны тексты вывода для соответствия стилю. Тексты вывода программы и README.md переработаны и приведены в соответствие с требованиями ТЗ.
